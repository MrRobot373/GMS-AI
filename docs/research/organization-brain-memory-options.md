# Build GEM AI's brain inside Postgres

GEM AI should build its organization brain itself, in TypeScript, in the Postgres 16 database it already runs. It should copy algorithms from open-source memory systems but not run any of them as the store of record. As of October 2026, no system (open or commercial) meets all of GEM AI's fixed constraints together: Postgres as the only datastore, per-project SQL permissions, local OpenAI-compatible models, a TypeScript runtime, a permissive licence and on-premises delivery. The closest candidates each miss at least one. Hindsight and the Mem0 OSS server run on Postgres and pgvector but are Python services with their own coarse tenancy. TencentDB Agent Memory has the best product concept and a DeepSeek Harness adapter, but it is beta and stores data in SQLite or MongoDB. Graphiti, Zep, MemOS and Cognee need a graph database, a cloud, or a paid licence. The research also changes *how* the brain should decide what to keep. Independent benchmarks show that memory systems mostly fail by **missing updates, not by inventing them**: Mem0 gets 25.5% of updates right and omits 74%. Adding every candidate to memory makes agents worse, and poisoned memories pass write-time content filters. So the write policy should be: keep every raw source, extract typed facts in background batches, supersede old facts with validity dates instead of deleting them, and require human acceptance for anything shared. The existing design in `docs/18-organization-brain.md` gets the main decision right (Option C, build in GEM AI). It needs a bi-temporal fact model, an entity and mention layer, trust tiers, a retrieval upgrade (the Knowledge module currently uses the unstemmed `simple` text-search config, no reranker and no vector index), and an operation-level evaluation before any automatic extraction ships.

## No off-the-shelf memory system fits all six constraints

The 2026 landscape differs from most 2025 comparison articles, and several commonly recommended systems have changed shape. **Mem0's open-source version removed both its ADD/UPDATE/DELETE algorithm and its graph memory**. Its v3 does "single-pass ADD-only" extraction, the migration guide states that "OSS has no graph memory replacement", and decay features raise an error outside the paid platform ([Mem0 migration guide](https://docs.mem0.ai/migration/oss-v2-to-v3), [mem0 main.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)). **Zep Community Edition is deprecated**, so Zep now runs only as a cloud or in the customer's own cloud (BYOC). Its open Graphiti engine needs Neo4j, FalkorDB or Neptune, and its reference servers "have no authentication, no authorization" ([getzep/zep README](https://github.com/getzep/zep/blob/main/README.md), [Graphiti README](https://github.com/getzep/graphiti/blob/main/README.md)). **Letta retired its Postgres-backed V1 server** in favour of a git-backed agent harness ([letta README](https://github.com/letta-ai/letta/blob/main/README.md)). LangMem has had no release since October 2025 ([PyPI langmem](https://pypi.org/project/langmem/)). Microsoft GraphRAG is "largely in maintenance mode" ([GraphRAG README](https://github.com/microsoft/graphrag/blob/main/README.md)).

Three findings matter most for GEM AI. First, only **Hindsight, the Mem0 OSS server, Honcho, MIRIX and memU can run on Postgres and pgvector alone**, and only Hindsight and Mem0 combine that with a permissive licence, wide adoption and a TypeScript client. Honcho's server is AGPL, which matters for software shipped to customers' premises ([Honcho README](https://github.com/plastic-labs/honcho/blob/main/README.md)). Second, **none of these systems understands GEM's permission model**: per person, per project, per workspace, enforced in SQL. Every option still requires GEM to re-check permissions before memory reaches a prompt. A memory store outside GEM's database makes that a cross-system join, and it puts personal data beyond GEM's existing export and delete paths. Third, the **published benchmarks cannot decide the choice**. Vendors claim first place on LoCoMo or LongMemEval using different answer models, judges and metrics (Supermemory's "#1" is a recall metric) ([Supermemory README](https://github.com/supermemoryai/supermemory/blob/main/README.md)). LoCoMo conversations fit in a context window and contain no knowledge-update questions ([Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). In Mem0's own 2025 paper, simply using the full context (72.90%) beat every memory system on accuracy ([arXiv 2504.19413](https://arxiv.org/html/2504.19413v1)). The memory benchmarks are conversational and English-language; none tests engineering documents, Hindi, or the gpt-oss, Nemotron or Gemma models GEM runs.

The commercial products teach more through their architecture than through their memory algorithms. Glean, Microsoft 365 Copilot, Gemini Enterprise, Atlassian Rovo and Dropbox Dash converge on the same stack. Connectors ingest content together with its ACLs. A hybrid lexical and vector index holds it. A graph links people, documents and activity under one canonical identity. Permissions are trimmed at query time, before anything reaches the model ([Glean docs](https://docs.glean.com/security/knowledge-graph), [Microsoft Learn](https://learn.microsoft.com/en-us/microsoftsearch/semantic-index-for-copilot)). Dropbox's engineering write-up is the most useful for GEM. Dropbox deliberately keeps its knowledge graph **out of a graph database** and builds it asynchronously into "knowledge bundles" that are chunked and embedded like documents. It also found that a canonical person ID was "very, very impactful", and that routing through raw MCP tools took up to 45 seconds against seconds through an index ([Dropbox Tech](https://dropbox.tech/machine-learning/vp-josh-clemm-knowledge-graphs-mcp-and-dspy-dash)). The anti-pattern is Writer's knowledge graph: "Permissions from the data source don't transfer over", so everyone with access to the graph sees everything in it ([Writer help](https://support.writer.com/articles/4599542578-setting-up-knowledge-graph-data-connectors)). Almost none of these products runs on-premises. This is GEM AI's opening with Indian engineering firms, provided the brain stays inside its own database.

## Deciding what to keep: append raw, extract in batches, supersede but never delete

The question "decides by itself what is worth keeping" has a clearer research answer than the vendor marketing suggests. The answer is to separate *keeping* from *promoting*. LongMemEval found that **storing only extracted facts or summaries loses information**. The best design keeps raw rounds as the stored values and uses extracted facts as extra index keys, which added 9.4% recall and 5.4% accuracy ([arXiv 2410.10813](https://arxiv.org/html/2410.10813v2)). Zep's own LongMemEval run shows the cost of trusting extraction alone: accuracy on questions about what the assistant itself had said fell from 94.6% to 80.4% ([arXiv 2501.13956](https://arxiv.org/html/2501.13956v1)). GEM already keeps the raw layer: document versions, chunks, chat messages and tasks. That layer should never be thinned by an importance score.

Promotion is where judgement belongs, and **adding everything to memory hurts**. In a study of agent experience memory, "add-all" memory scored 13.05 against 38.50 for quality-gated addition and 42.34 for gating plus deletion. A vanilla LLM judge used as the gate could be worse than no gate at all ([arXiv 2505.16067](https://arxiv.org/html/2505.16067v2)). The cheap signals for importance work better than one LLM rating per item. These are: structural priors by content type (decisions, owners, deadlines, prices, procedures); usage heat, as in MemoryOS's `visits + interaction length + exp(−Δt/μ)` ([arXiv 2506.06326](https://arxiv.org/html/2506.06326)); outcome signals; and a salience score returned by the same extraction call. The classic Generative Agents formula, recency + importance + relevance with exponential recency decay, remains a sound ranking template ([arXiv 2304.03442](https://ar5iv.labs.arxiv.org/html/2304.03442)). Glean shows the product version: learned memories are consolidated daily, versioned, audit-logged and "age out gradually", and answers that used memory show an icon ([Glean admin docs](https://docs.glean.com/administration/assistant/configuration/memory-personalization)).

Background batching beats extraction on every turn, on both cost and accuracy. LightMem's filter-then-consolidate pipeline with offline ("sleep-time") updates cut total tokens by up to 38× and API calls by up to 30×, while *raising* accuracy on LongMemEval ([arXiv 2510.18866](https://arxiv.org/abs/2510.18866)). Sleep-time compute matched accuracy with about 5× less compute at answer time, and the gain was largest where queries are predictable ([arXiv 2504.13171](https://arxiv.org/abs/2504.13171)). Project status and team FAQs are exactly that kind of query. Building the memory is the expensive step: on HaluMem-Medium, ingestion took Mem0 about 2,768 minutes against 20–140 minutes for retrieval ([arXiv 2511.03506](https://arxiv.org/html/2511.03506v3)).

Updates and contradictions are the weakest point of every system tested. On HaluMem-Medium, update correctness was **25.5% for Mem0 (74.0% omitted), 47.3% for Zep, and 62.1% for the best system, MemOS**. Update hallucination stayed under 2% only because few updates were attempted at all ([arXiv 2511.03506](https://arxiv.org/html/2511.03506v3)). Author names suggest HaluMem shares researchers with MemOS, so MemOS's lead deserves caution, but the omission pattern holds across every vendor tested. On MemoryAgentBench's selective-forgetting task, "all methods fail on the multi-hop situation (with achieving at most 28% accuracy)" ([arXiv 2507.05257](https://arxiv.org/html/2507.05257v4)). Mem0 itself says staleness remains an open problem ([Mem0 blog](https://mem0.ai/blog/state-of-ai-agent-memory-2026)). The pattern that holds up is Graphiti's **bi-temporal, non-destructive supersession**. Each fact records when it was true (`valid_from`, `valid_to`) and when the system learned and expired it. Contradiction candidates come only from facts about the same entities. A contradicted fact gets an end date rather than being deleted, and graph writes run through predefined queries, never LLM-generated ones ([arXiv 2501.13956](https://arxiv.org/html/2501.13956v1)). For GEM, narrowing candidates to the same subject and predicate turns most contradiction checks into a rule. Deadline, owner, status and approver are single-valued attributes where a newer statement simply closes the old row. The LLM is kept for genuinely ambiguous cases. Relative dates ("next Friday") should be normalized at write time by the larger model, because 8B-class models "often hallucinat[e] or miss temporal cues" ([arXiv 2410.10813](https://arxiv.org/html/2410.10813v2)).

Small open models can do this work if the prompts and schemas constrain them. Hindsight's paper reports that an open 20B backbone rose from 39% (full context) to 83.6% with its memory design ([arXiv 2512.12818](https://arxiv.org/abs/2512.12818)); the paper does not confirm the model was gpt-oss-20b. Memory-R1 trained a write manager on only 152 QA pairs and raised a LLaMA-3.1-8B LoCoMo score from 45.68 (Mem0) to 62.74 ([arXiv 2508.19828](https://arxiv.org/html/2508.19828)). gpt-oss-20b runs within 16 GB and gpt-oss-120b on a single 80 GB GPU, and both support structured outputs ([gpt-oss-120b model card](https://huggingface.co/openai/gpt-oss-120b)). Ollama enforces a JSON schema through its `format` field ([Ollama docs](https://github.com/ollama/ollama/blob/main/docs/capabilities/structured-outputs.mdx)). **No published study measures gpt-oss, Nemotron or Gemma as memory extractors**, so GEM must measure this itself.

Poisoning makes human review of shared memory a security control, not a usability nicety. MINJA showed that ordinary users, issuing only normal queries, can plant malicious memories with about **98.2% injection success** ([arXiv 2503.03704](https://arxiv.org/html/2503.03704)). In 2026, false statements in just 1.2% of a corpus cut accuracy from 0.850 to 0.300. A four-stage write-time screen caught 83% of prompt injections but **rejected none of 360 poisoned memories**, because telling true from false needs outside grounding ([arXiv 2608.21230](https://arxiv.org/abs/2608.21230)). SpAIware showed an untrusted web page writing persistent instructions into ChatGPT memory ([Embrace The Red](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/)). Writes to GEM's brain therefore need trust tiers by channel. Curated documents and admin input rank highest, then statements by authenticated employees, then agent or tool output, then external web or email content. Lower tiers may write only to scoped memory, never to organization memory without review. The brain should never store imperative instructions, and it should cap how many retrieved items any one source can contribute to a single answer.

## A graph pays off for multi-hop questions, not for daily spec lookups

Most questions engineers ask GEM will be local and detail-oriented: the rated current of a motor, clause 7.3 of a specification, the IP rating Acme asked for. On those questions, independent studies find **plain RAG with a reranker matches or beats graph RAG**. GraphRAG-Bench measured fact retrieval at 60.92 for RAG with reranking against 49.29 for Microsoft GraphRAG and 58.62 for LightRAG. Graph methods won on complex reasoning (HippoRAG 2 at 53.38) and on contextual summarization (GraphRAG at 64.40) ([arXiv 2506.05690](https://arxiv.org/html/2506.05690)). A debiased evaluation found that many reported GraphRAG gains become "much more moderate or even vanish", because LLM-judge win rates swing by more than 30% with answer order alone ([arXiv 2506.06331](https://arxiv.org/abs/2506.06331)). HippoRAG 2 is the one method that beat a strong dense retriever on both simple and multi-hop QA (59.8 against 57.0 average F1). It did so at **9.2M indexing input tokens against 115.5M for GraphRAG** on the same 11,656-passage corpus, with 1.2-second queries ([arXiv 2502.14802](https://arxiv.org/html/2502.14802)). Its design uses the graph only to *route* retrieval back to the original passages, which then carry the citations. That matches GEM's citation and permission model far better than answers built from LLM-written entity summaries.

Permissions settle the design question. Merged entity descriptions and community reports **mix text from documents with different access rights**. No open framework filters graph retrieval by document ACL, and research shows graph RAG leaks structured entity and relationship information ([arXiv 2508.17222](https://arxiv.org/pdf/2508.17222v1)). The safe structure stores *mentions*, not just merged facts: `entity_mention(entity_id, chunk_id, document_version_id)` and its relation equivalent. An entity or edge is then visible only when at least one mention the user may open supports it. Any precomputed summary is built per permission scope, and global questions are summarized lazily at query time over permitted chunks only. Even a bare edge such as "Project A — supplier — Vendor B" can be confidential.

Postgres needs no graph extension for this. LightRAG, the most active open graph-RAG framework, now recommends plain JSONB and B-tree tables over Apache AGE and measured them about **28× faster** on graph fetches ([LightRAG API server doc](https://github.com/HKUDS/LightRAG/blob/main/docs/LightRAG-API-Server.md)). SQL/PGQ was committed to PostgreSQL 19 in March 2026 and then rolled back ([depesz](https://www.depesz.com/?p=4467)). Kùzu is archived ([Kuzu README](https://github.com/kuzudb/kuzu)). FalkorDB is SSPL and Memgraph is BSL ([FalkorDB LICENSE](https://github.com/FalkorDB/FalkorDB/blob/master/LICENSE.txt), [Memgraph LICENSE](https://github.com/memgraph/memgraph/blob/master/LICENSE)). Entity, mention and relation tables with recursive CTEs cover the 1–3 hop expansions an organization brain needs. Domain entities such as part numbers, equipment tags, IEC and IS standards, project codes and customer names are better caught by regex and dictionary extractors than by open LLM extraction, which is the schema-bounded approach of KAG and Youtu-GraphRAG ([arXiv 2508.19855](https://arxiv.org/abs/2508.19855)).

## Postgres 16 can carry the brain, but Knowledge search needs four upgrades first

Scale is not the constraint. A hundred thousand pages plus a few million memory items comes to about 1–10M vectors. At 1024 dimensions stored as `halfvec`, that is roughly 12 GB before index overhead, well inside single-node benchmarks: AWS tested 10M vectors with pgvector 0.8 ([AWS blog](https://aws.amazon.com/blogs/database/supercharging-vector-search-performance-and-relevance-with-pgvector-0-8-0-on-amazon-aurora-postgresql/)). Retrieval quality is the constraint, and reading the repository shows four gaps that would carry straight over to brain search if `brain_item` simply "reuses Knowledge's hybrid search", as doc 18 proposes.

First, `retrieveKnowledge` in `apps/api/src/services/knowledge.ts` and the generated `tsv` column in `packages/db/src/schema.ts` both use **`to_tsvector('simple', …)`**. That config does no stemming in either language, although PostgreSQL 16 ships a Snowball `hindi` configuration, which also stems Latin-script words as English ([snowball_create.pl](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/snowball/snowball_create.pl)). Ranking uses `ts_rank_cd`, which has no inverse document frequency and is not BM25 ([Tiger Data](https://www.tigerdata.com/blog/pg-textsearch-bm25-full-text-search-postgres)). The best permissively licensed BM25 extension, pg_textsearch, supports **only PostgreSQL 17 and 18**, while ParadeDB's PG16-compatible alternative is AGPL ([pg_textsearch README](https://github.com/timescale/pg_textsearch), [ParadeDB LICENSE](https://github.com/paradedb/paradedb/blob/main/LICENSE)). The practical path is per-language `hindi` and `english` tsvectors now and a planned PG18 upgrade. PG18 also brings `WITHOUT OVERLAPS` temporal constraints and `uuidv7()` ([PG18 release notes](https://www.postgresql.org/docs/release/18.0/)).

Second, the `embedding` column is an untyped `vector` with **no ANN index**, so every vector query is an exact scan. That gives perfect recall today but will not hold at millions of rows. pgvector cannot index an untyped column directly. GEM needs per-model expression or partial HNSW indexes, and it must turn on iterative scans, because permission predicates are applied *after* the HNSW traversal. In pgvector's own example, with default settings a filter matching 10% of rows returns about 4 results instead of 40 ([pgvector README](https://github.com/pgvector/pgvector#iterative-index-scans)). Iterative scans in 0.8.0 cut one filtered query's p99 latency from 123 ms to 13 ms in AWS's vendor test. Small permitted corpora should stay on exact search.

Third, there is **no reranker**, and a reranker is the largest cheap gain in the literature. Anthropic's contextual retrieval cut top-20 retrieval failures by 49%; adding reranking took the cut to 67% ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). Ollama has no rerank endpoint ([Ollama API docs](https://github.com/ollama/ollama/blob/main/docs/api.md)), so a reranker means a second local service: TEI for bge-reranker-v2-m3, or vLLM's `/rerank` for Qwen3-Reranker. The vendor-reported multilingual reranking scores are 66.36 for Qwen3-Reranker-0.6B and 58.36 for bge-reranker-v2-m3 ([Qwen3-Reranker model card](https://huggingface.co/Qwen/Qwen3-Reranker-8B)). Fourth, contextual chunk headers are missing: document title, section path, equipment tags and revision, prepended before both embedding and keyword indexing.

The rest of the building blocks are settled and permissively licensed. pg-boss (MIT, Node ≥22.12) provides debounce, cron, retries and dead-letter queues on Postgres ([pg-boss README](https://github.com/timgit/pg-boss)). graphile-worker's `job_key` allows deduplicated enqueueing from SQL triggers in the same transaction as a new document version ([Graphile Worker docs](https://worker.graphile.org/docs/job-key)). On PG16, a btree_gist exclusion constraint enforces non-overlapping validity intervals until PG18's `WITHOUT OVERLAPS` arrives ([PG16 btree_gist](https://www.postgresql.org/docs/16/btree-gist.html)). For Hindi and English embeddings, the vendor scores favour Qwen3-Embedding-0.6B (Apache-2.0, multilingual retrieval 64.64 against 54.60 for bge-m3) ([Qwen3-Embedding model card](https://huggingface.co/Qwen/Qwen3-Embedding-8B)). bge-m3 (MIT), however, has independent Hindi-BEIR evidence ([arXiv 2409.05401](https://arxiv.org/html/2409.05401)). jina-embeddings-v3 and jina-reranker-v2 are non-commercial and should be avoided ([jina-reranker-v2](https://huggingface.co/jinaai/jina-reranker-v2-base-multilingual)).

## How the research confirms, changes and extends doc 18

The existing proposal holds up on its central choices, and the research sharpens almost every mechanism beneath them.

| Doc 18 position | Verdict | What the research adds |
|---|---|---|
| Option C: build in GEM AI on its own Postgres, permissions and UI | **Confirmed** | No external system meets all six constraints; GEM's per-project SQL permissions are already stronger than most open platforms offer |
| TencentDB Proxy (A1) unsuitable for multi-user | **Confirmed** | Its delete endpoints trust a service key, not a user |
| TencentDB API (A2) as a later optional connector | **Downgrade** | Still beta (v2.0.3-beta.1, not "2.0.0"); "Editable memories: L1 - L3" is still on the roadmap; the "proven benchmark gain" is a self-reported PersonaMem figure. Copy its layer model and Wiki idea; do not plan an integration. |
| Shared memory only after a person accepts | **Confirmed and strengthened** | Required by the poisoning evidence; write-time content filters miss false facts |
| Personal memory automatic if the person opts in | **Change** | Auto-capture only from the person's own statements, never from retrieved documents or tool output (SpAIware, the 2026 Claude memory attack) |
| Status `proposed/active/replaced`, `valid_from`, `replaced_by` | **Extend** | Full bi-temporal fields (`valid_from/valid_to`, `recorded_at/expired_at`), a subject + predicate structure so contradiction checks can be narrowed, a trust tier, and a salience field |
| Every conflict shown side by side to a person | **Change** | Rule-based supersession for single-valued attributes, LLM resolution only for ambiguous ones, people only for shared scopes. Add a periodic stale-fact sweep, because the dominant failure is a *missed* update, which an on-write conflict check never sees. |
| A fast-tier call after every chat turn or task | **Change** | Debounce to session end and batch; piggyback salience on the same call; skip acknowledgement-only turns |
| `brain_source` (kind, ref_id, quote) | **Extend** | Store the document version id and character offsets, and verify quotes by string match; re-versioning a document then supersedes every fact derived from it |
| Entity pages (customers, suppliers, standards) | **Extend** | Canonical entity + mention + relation tables with mention-level permission filtering; regex and dictionary extractors for tags and standards; canonical person IDs |
| Nightly project-page rewrite | **Confirmed, with a constraint** | Pages must be permission-homogeneous: an organization page can never summarize project-restricted items |
| Retrieval "reuses Knowledge's hybrid search" | **Change** | Fix that search first: language configs, HNSW with iterative scans, a reranker, contextual headers. Use memory as an index into its sources, and re-read the cited document version for numbers and contract terms. |
| Retention left as an open question | **Extend** | Never delete the raw layer; type-dependent decay for ranking (decisions slow, status fast); Guru-style verifiers and review intervals for organization items ([Guru help](https://help.getguru.com/docs/verifying-and-unverifying-cards)) |
| 30 questions per pilot project, denial probes | **Confirmed and extended** | Add HaluMem-style operation metrics: extraction precision and recall, update correct/omitted, stale-answer rate, citation validity, poisoning red-team |

Two product-level conclusions also follow. Chat should *search* memory through a tool call rather than receive an auto-injected profile. That is Claude's model-invoked pattern, and it avoids the hidden-context problems Simon Willison documented in ChatGPT ([Simon Willison](https://simonwillison.net/2025/May/21/chatgpt-new-memory/)). A short project page can still be injected automatically. Second, memory must sit under GEM's audit log and retention rules. Microsoft's Copilot memory shows the failure to avoid: "Purview retention policies don't apply" and memory actions "don't generate audit log entries" ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/copilot/copilot-personalization-memory)).

## Recommended architecture: five layers in one database

The recommended brain has five layers, all stored in GEM's Postgres and all read through one permission predicate.

**L0, sources.** These are the existing document versions, chunks, chat messages and Work AI tasks, extended with an event time and a language tag. They are immutable apart from supersession. **L1, memory items.** The `brain_item` table holds typed atomic facts, decisions, preferences, procedures and statuses. Each item carries a subject, predicate and object; bi-temporal validity; confidence; salience; trust tier; status; scope; and one or more `brain_source` rows pointing at L0 spans. **L1.5, entities.** The `entity`, `entity_mention` and `relation` tables cover people, customers, suppliers, equipment, standards and projects. They link to chunks and items, and a user sees an entity only through mentions they may open. **L2, pages.** Versioned project pages, entity pages and procedure pages are each built within a single permission scope; procedures are promoted into Work AI skills. **L3, profiles.** The personal preference profile is private to its owner. A small organization profile is curated by admins or named knowledge owners.

The write path runs on pg-boss jobs keyed by `(source id, version, step, content hash)`, so that re-runs are idempotent. A cheap pre-filter without any LLM drops boilerplate, flags personal data and credentials, and skips near-duplicates. gpt-oss-20b then extracts typed facts from debounced chat sessions and from high-prior document sections, using schema-constrained output. A resolver compares each fact against the top 10 valid facts with the same subject and predicate and returns ADD, SUPERSEDE, INVALIDATE or NOOP. It never hard-deletes. A nightly gpt-oss-120b job does date normalization, contradiction checks, page rewrites, duplicate merges and the stale-fact sweep. Items in personal scope from the owner's own statements are activated directly. Items in project and organization scope enter a review queue that shows a diff.

The read path is a single `brain_search` service. It is exposed to Chat as a tool, and to Work AI, Code and DeepSeek Harness agents as a tool or MCP endpoint, together with a `brain_propose` write tool. It applies GEM's permission SQL first, then runs language-aware keyword search and HNSW vector search over items, entities and chunks, fuses them with RRF (k=60 to start, a tuned convex combination later ([arXiv 2210.11934](https://arxiv.org/abs/2210.11934))), and reranks the result. It returns valid items *with their source snippets*, so every answer can cite down to the page. DeepSeek Harness already has memory plugins (TencentDB, MemOS's local SQLite bundle, ReMe's Markdown store) ([ReMe README](https://github.com/agentscope-ai/ReMe/blob/main/README.md)). Each of them would create a second store outside GEM's permissions, so Code and Work AI should call the GEM brain instead.

### Build, borrow, and benchmark one adopt candidate

The decision is to **build the core and borrow the parts**. The algorithms to borrow, all under permissive licences, are: Mem0 v3's extraction and dedupe prompt (Apache-2.0), Graphiti's `resolve_edge` contradiction prompt and bi-temporal model (Apache-2.0), Hindsight's evidence-carrying observations (MIT), TencentDB's L0–L3 layers and document-to-Wiki pages (MIT), HippoRAG 2's route-to-passage graph use, and Karpathy's ingest/query/lint loop for project pages ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). The components to adopt are pg-boss, TEI or vLLM serving a reranker and embedder, and pg_textsearch once GEM is on PG18. Hindsight is the one system worth running, but only as an evaluation baseline on GEM's own test set, not in production. If GEM's own build cannot match it on update correctness, a Hindsight sidecar on the same Postgres becomes the fallback, because its MIT licence, pgvector storage and TypeScript client make that swap cheap.

| Risk | Mitigation |
|---|---|
| Extraction misses facts or invents them (recall below 60% across HaluMem systems) | Raw layer always kept; answers cite and re-read sources; operation-level evaluation before auto-extraction ships |
| Stale facts used after a change | Bi-temporal supersession, rules for single-valued attributes, nightly stale-fact sweep, only valid rows in answers |
| Leaks through derived pages or entity edges | Mention-level filtering, scope-homogeneous summaries, one permission SQL predicate, denial probes in CI |
| Memory poisoning | Trust tiers, review for shared scopes, no stored instructions, per-source occupancy caps |
| Silent recall loss from post-filtered HNSW | Iterative scans, exact search for small scopes, recall regression test |
| Hindi quality | Language-tagged tsvectors, a multilingual embedder and reranker chosen on GEM's own Hindi set |
| Local-model throughput and cost | Batching and debounce, 20B for routine work and 120B only nightly, measured tokens/s on GEM hardware |
| Licence exposure on customer sites | Avoid AGPL, SSPL, BSL and non-commercial components (ParadeDB, VectorChord, FalkorDB, Memgraph, Jina v2/v3) |

GEM should evaluate four things first, in this order, because each one gates a design choice. The first is the extraction bake-off: gpt-oss-20b, gpt-oss-120b, Nemotron and Gemma on the annotated English and Hindi chunks, scored on precision, recall and temporal normalization. The second is filtered recall and latency of HNSW against exact search under real permission shapes. The third is embedder and reranker choice on Hindi and English engineering queries. The fourth is a Hindsight baseline run on the same 30 questions per project, including deadline changes and document re-versions.

## Conclusion

Picking a memory product matters less than picking a write policy. The field moved in 2025–26 from LLM-adjudicated UPDATE/DELETE toward append-only records, validity intervals and background consolidation. The reason is that destructive updates proved unreliable, and the independent data shows the hard part is *noticing* that something changed. That turns GEM AI's assets into advantages: a versioned document store, numbered citations and SQL permissions are the provenance and supersession machinery that memory frameworks bolt on later. Built that way, the brain is less a new store than a typed, dated, permission-filtered index over evidence GEM already holds. That is why building inside Postgres is cheaper and safer than adopting a system.

One weakness cuts across every option: no public benchmark tests enterprise documents, knowledge updates, Hindi or the open models GEM deploys. The first deliverable should therefore be GEM's own evaluation set, not a feature. The same set doubles as a moat. Once it exists, any vendor claim, model upgrade or framework swap can be settled in an afternoon on GEM's own data rather than argued from leaderboards.
